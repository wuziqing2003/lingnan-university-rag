# RAG 优化实验报告

> 项目背景：基于岭南师范学院教务相关规章 PDF 搭建的问答系统  
> 语料规模：约 67 份 PDF，入库后约 1474 个文本块  
> 本文记录切块、混合检索、Rerank 精排、Ragas 有无精排对照（现 50 题），以及拒答 / 幻觉行为小金标回归（现 30 题）的过程与结果

---

## 实验一：Chunking 策略对照

### 1. 实验目标

学校规章里经常是「第×条」「（一）（二）」这种结构。如果按固定字数硬切，很容易把一条完整规定劈成上下两半，检索时就只捞到一半。

这次主要对比三种切法：

1. **Naive 硬切**：`text[i:i+chunk_size]`，到长度就截断。
2. **CharacterTextSplitter**：`separator=""`，相当于 LangChain 版的固定字符切块。
3. **RecursiveCharacterTextSplitter**：优先按段落、换行、句号等边界切，实在找不到才硬切。

想搞清楚两件事：

- 固定长度切块是不是很容易腰斩句子/条款？
- `128 / 256 / 512` 里，哪个更适合当学校规章的默认参数？

### 2. 实验设置

| 项目 | 设置 |
|------|------|
| 样本文档 | 《岭南师范学院普通全日制本科生学籍管理规定（2025 年修订）》 |
| 样本范围 | 第一条至第九条 |
| 样本长度 | 1563 字符 |
| Chunk Size | 128、256、512 |
| Chunk Overlap | 0（先不加重叠，方便观察边界问题） |
| 长度计算 | Python `len`，按字符计数 |
| Recursive 分隔符 | `["\n\n", "\n", "。", "；", "，", " ", ""]` |
| 实验脚本 | `playground/chunk_test.py` |
| 固定样本 | `data/chunk_experiment_sample.txt` |

选这份样本，主要是因为条款编号清楚，句子偏长，还有列举项，比较容易看出切坏没切坏。

### 3. 结果

#### 3.1 客观统计

| 方法 | Size | 块数 | 最短块 | 最长块 | 平均长度 | 以句末标点结束 | 小于 64 字的块 |
|------|-----:|-----:|-------:|-------:|---------:|-----------------:|----------------:|
| Naive | 128 | 13 | 27 | 128 | 120.0 | 1 | 1 |
| Character | 128 | 13 | 27 | 128 | 120.0 | 1 | 1 |
| Recursive | 128 | 14 | 93 | 126 | 110.6 | 6 | 0 |
| Naive | 256 | 7 | 27 | 256 | 223.0 | 1 | 1 |
| Character | 256 | 7 | 27 | 256 | 223.0 | 1 | 1 |
| Recursive | 256 | 8 | 35 | 254 | 194.4 | 1 | 2 |
| Naive | 512 | 4 | 27 | 512 | 390.5 | 1 | 1 |
| Character | 512 | 4 | 27 | 512 | 390.5 | 1 | 1 |
| Recursive | 512 | 4 | 44 | 512 | 389.8 | 1 | 1 |

补充说明：

- 「以句末标点结束」只统计 `。；！？`，用来辅助看边界，不等于语义一定完整。
- Recursive 也可能在换行处切开，所以不能只盯着句末标点数量。
- 这次 overlap 设成 0，生产里用的 overlap 要另看。

#### 3.2 主要观察

**Naive 和 Character 基本是一回事。** Character 设了 `separator=""` 之后，块数、长度、切点都和手写硬切差不多，相当于 LangChain 提供的固定切块写法。

**固定长度切块确实容易腰斩。** 到字数上限就截，不管是不是句中、条中、列举中间。把 size 调大只能少切几次，解决不了边界问题。

**Recursive 更愿意顺着文档结构走。** 它会按分隔符优先级找切点，找不到才硬切。128 字那组里，以句末结尾的块明显更多一些。

**Recursive 也会出现短残块。** 256 字那组里有 35、44 字这种偏短的块，说明递归切并不能保证每块大小都均匀。

**PDF 抽出来的换行会干扰判断。** 原文「复查」被抽成 `复\n查`，用完整字符串做匹配时会对不上。这是抽取和评估规则的问题，不代表切块把内容弄丢了。

### 4. 参数结论

项目里最终用的生产参数是：

```text
splitter = RecursiveCharacterTextSplitter
chunk_size = 256
chunk_overlap = 50
separators = ["\n\n", "\n", "。", "；", "，", " ", ""]
length_function = len
```

为什么选 256：

- **128**：块更细，但长条款容易被拆碎，上下文不够。
- **256**：条款完整度、块数量、检索粒度之间比较折中。
- **512**：上下文更全，但一块里可能混进好几条不同规定，噪声会变大。

`chunk_overlap=50` 没有放进这次受控对比，生产里先用作降低边界信息丢失的缓冲。

### 5. 对项目的影响

结论已经落到 `scripts/ingest_pdfs.py`：

- 固定长度切片换成 `RecursiveCharacterTextSplitter`；
- 默认 `chunk_size = 256`，`chunk_overlap = 50`；
- Chroma 重新入库：67 份 PDF，约 1474 个 chunk。

### 6. 实验局限

这次只说明了切块边界上的差异，还不能直接证明问答准确率一定更高。

具体局限：

1. 只用了一份文档里大约 1563 字的样本；
2. 边界质量主要靠人工看和简单统计；
3. 没有对比 overlap 0 和 50 对检索的影响；
4. 没有算 Hit@3、Context Precision 或最终回答质量；
5. PDF 断行会干扰切块观察和金标准匹配。

所以这一部分只讨论切块边界和参数选择，不把它说成「问答已经变准了」。

## 实验二：混合检索（Hybrid Search）

### 1. 实验目标

Chroma 自带稠密向量检索，但没有现成的 BM25 关键字检索。问学校规章时，其实会碰到两类问题：

- **语义类**：比如「奖学金和助学金有什么区别」；
- **专名 / 精确词类**：比如岗位名、条款主题词。

这次在不改 Chroma 内核的前提下，加了一层轻量的 `rank_bm25`，和向量检索并行，再用 RRF（互惠倒数排名）把两路结果合在一起，看混合检索会不会比纯向量更稳。

主要想确认：

1. 能不能在现有向量库上稳定接上 BM25 + RRF？
2. 在真实校规章语料上，Hybrid 和 Dense 的 Top3 差在哪？
3. 中文分词（正则 vs jieba）对 BM25 影响有多大？

### 2. 实验设置

| 项目 | 设置 |
|------|------|
| 向量库 | Chroma `lingnan_rag_pdfs` |
| 语料规模 | 约 67 份 PDF / 1474 chunks |
| Embedding | `BAAI/bge-large-zh-v1.5`（硅基流动） |
| 向量通道 | Chroma `query_embeddings`，候选数 `CANDIDATE_N = 10` |
| 关键字通道 | `rank_bm25.BM25Okapi`，候选数 10 |
| 融合算法 | RRF，`k = 60` |
| 最终返回 | Top 3 文本块 |
| 中文分词 | 初版：正则；定稿：`jieba` + 领域词表 |
| 对照脚本 | `scripts/retrieve_probe.py` |
| 实现文件 | `app/rag/hybrid.py` |

**验收问句：**

| 类型 | 问句 |
|------|------|
| 专名 / 流程 | 研究生三助一辅岗位怎么申请？ |
| 语义区分 | 研究生国家奖学金和国家助学金有什么区别？ |

**流程大致是：**

```text
问题
  ├─ Dense：问题 Embedding → Chroma Top-10 → id 排名
  ├─ BM25：jieba 分词 → 全库打分 → Top-10 → id 排名
  └─ RRF：对两路 id 累加 1/(k+rank) → 取 Top-3 正文
```

两路用文档 id 对齐。id 入库时按 `文件名_序号` 写入；BM25 索引通过 `collection.get` 把全库文本拉进内存再构建。

### 3. 结果

#### 3.1 分词修正前后

初版用的是正则：

```python
re.findall(r"[\u4e00-\u9fff]+|[a-zA-Z0-9]+", text)
```

连续汉字经常被当成一个超长 token，BM25 基本失灵，Hybrid Top3 里甚至出现过和实践教学无关的噪声文档。

后来改成 jieba，并给这些专名加了 `add_word`：

- 三助一辅
- 国家奖学金
- 国家助学金
- 学业奖学金
- 保留入学资格
- 学业预警
- 勤工助学

改完之后，「研究生三助一辅岗位怎么申请？」能正确切出「三助一辅」，BM25 通道才真正可用。后面对照都基于 jieba 版本。

#### 3.2 Dense 与 Hybrid 对照

**问句 A：研究生三助一辅岗位怎么申请？**

| 通道 | Top1 | Top2 | Top3 |
|------|------|------|------|
| Dense | 《三助一辅岗位管理办法》申请条件 / 不得受聘相关段落 | 同文件：岗位职责 + 申请基本条件 | 同文件：岗位管理与考核 |
| Hybrid | 同 Dense Top1 | 同文件：岗位职责 + 申请基本条件 | 同文件：**第七条聘用程序**（设岗→公布→应聘→录用） |

观察：

- 两路 Top3 都落在正确文件里，没有再明显跑题；
- Dense 已经能稳住目标文件；
- Hybrid 把更直接回答「怎么申请」的聘用程序段拉进了 Top3，但还没排到 Top1；
- Top1 / Top2 经常是「申请条件」或「岗位职责」，同主题，但不是最贴「流程」的那一段。

**问句 B：研究生国家奖学金和国家助学金有什么区别？**

| 通道 | Top1 | Top2 / Top3 概况 |
|------|------|------------------|
| Dense | 奖助学金办法里对奖学金、学业奖学金、助学金用途的定义段 | 同文件停发、申报与评审相关条款 |
| Hybrid | 与 Dense 相同的定义段 | 同文件评审原则、停发与申报相关条款 |

这题两边差别不大：专名清楚、语义也清楚时，纯向量已经够用。

### 4. 结论

1. **工程上能跑通。** 不用改 Chroma，用 `rank_bm25` + RRF 就能接混合检索，并且已经接到对话链路里的 `retrieve`。
2. **中文分词是 BM25 的前提。** 正则整段切词会把关键字通道搞废；jieba + 领域词表之后，跨主题噪声明显少了。
3. **这批验收问句上，Dense 基线已经不差。** Hybrid 更像是把目标文档稳住，并把部分更贴题的段落带进 Top3，而不是全面碾压 Dense。
4. **瓶颈开始从「召不回」变成「排不准」。** 「怎么申请」那题，聘用程序已经进 Top3，但排序还压在条件/职责后面，后面需要更细的相关性重排。

### 5. 对项目的影响

相关代码已落地：

- `app/rag/hybrid.py`：Dense + BM25 + RRF；
- `app/rag/chain.py`：`retrieve` 先接 `hybrid_search`（实验三再叠 Rerank）；
- `scripts/retrieve_probe.py`：Dense / Hybrid 对照探针；
- 依赖：`rank_bm25`、`jieba`。

### 6. 实验局限

1. 验收问句不多，不能当成全库所有题型都提升了；
2. 评估主要靠人工看 Top3 预览，还没算 Hit@3、MRR 或 Ragas；
3. RRF 只融合排名，不太分得清「同文件次相关」和「直接答问」；
4. 切块边界有时会把职责和条件挤在同一段预览里，人工判断会变难；
5. 这一步还没上跨编码器 Rerank，「正确块在池子里但排得靠后」交给实验三。

这一阶段更适合表述成：混合检索双通道可用，关键字侧更稳了；排序精度还有空间，适合作为后面 Rerank 的前置条件。

## 实验三：Rerank 二次精排

### 1. 实验目标

实验二里已经能感觉到：专名清楚的规章问句上，Dense / Hybrid 往往能稳住目标文件，麻烦更多出在排序。比如「研究生三助一辅岗位怎么申请？」——更直接回答流程的「第七条聘用程序」已经进 Hybrid Top3，但经常排在「申请条件 / 岗位职责」后面。

RRF 只看两路名次，不会直接判断「这段文字是不是最贴当前问题」。所以这次在 Hybrid 初筛结果上接了一个跨编码器式 Rerank，对候选再打一遍相关性分，看进入生成阶段的 Top3 能不能排得更合理。

主要想确认：

1. 能不能在现有 Hybrid 链路上稳定接云端 Rerank API？
2. Hybrid Top10 精排之后，相关块在 Top3 里的位置有没有变好？
3. Rerank 能解决什么、解决不了什么？

### 2. 实验设置

| 项目 | 设置 |
|------|------|
| 初筛 | `hybrid_search`，`n_results=10`（Dense + BM25 + RRF） |
| 精排模型 | `BAAI/bge-reranker-v2-m3`（硅基流动 `/v1/rerank`） |
| 精排输入 | Hybrid 返回的 Top10 正文 |
| 精排输出 | 重排后 Top3 正文 |
| 实现文件 | `app/rag/rerank.py` |
| 链路接入 | `app/rag/chain.py`：`hybrid_search(10)` → `rerank_documents(..., 3)` |
| 对照脚本 | `scripts/retrieve_probe.py`（`probe_rerank` / `compare_hybrid_vs_rerank`） |
| 评估方式 | 人工看预览 + 金标关键词位次（`hit_rank`） |

**流程：**

```text
问题
  └─ Hybrid：Dense + BM25 + RRF → Top10 候选正文
        └─ Rerank：query × 各候选成对打分 → 按相关性重排 → Top3
              └─ join 为 context → Prompt → LLM
```

需要记住几点：

- Rerank **不会重新搜全库**，只在初筛池里重排；池子里没有的块捞不回来。
- API 返回的是候选下标 `index`（本项目 `return_documents=False`），再映射回原文。
- 候选为空直接返回；只有 1 条时跳过 API。

**探针问句与金标关键词（示例）：**

| 问句 | 金标关键词 |
|------|------------|
| 本科生勤工助学怎么申请？ | 勤工助学 |
| 普通全日制本科生转专业需要什么条件？ | 转专业 |
| 新生可以申请保留入学资格吗？期限多久？ | 保留入学资格 |
| 缓考怎么申请？ | 缓考 |
| 教学事故怎么认定？ | 教学事故 |

`hit_rank` 会看 Top3 里有没有同时包含全部金标词的块；有就返回名次（1/2/3），没有就算未命中。

### 3. 结果

#### 3.1 工程接入

已经验证这条链路能跑：

1. Hybrid 产出 Top10 字符串列表；
2. 调硅基流动 Rerank 接口完成重排；
3. `retrieve` 把精排后的 Top3 拼进生成上下文；
4. 探针可以同时打印 Hybrid Top10 和 Rerank Top3，并对比两边的金标位次。

#### 3.2 Hybrid Top3 与 Rerank Top3 对照

对照方式和实验二类似：同一问句下比较「只取 Hybrid 前三」和「Hybrid Top10 再 Rerank 取三」。

主要观察：

1. **Rerank 对准的就是实验二里的排序问题。**  
   目标流程/条件段已经在 Hybrid 候选池里时，精排有机会把更贴「怎么申请 / 怎么认定」的块往前推，压低同文件里的职责说明、背景介绍。

2. **本来 Top1 就对的问句，收益不一定明显。**  
   语义清楚、专名完整时，Hybrid（甚至 Dense）Top1 往往已经够用，Rerank 更多是微调顺序。

3. **金标关键词太粗时，数字不太敏感。**  
   比如只用「勤工助学」「转专业」，好几段同主题块都能命中，名次分不太清「次相关」和「直接回答」。人工看预览还是必要的。

4. **Rerank 补不了初筛漏召回。**  
   正确块没进 Hybrid Top10，精排也无能为力；这时该回头看分词、切块或候选数，而不是只调 Rerank。

#### 3.3 和实验二怎么衔接

| 阶段 | 主要作用 | 还剩什么问题 |
|------|----------|--------------|
| Dense / Hybrid | 稳住目标规章、减少跑题 | 同主题次相关块可能压过直接答问块 |
| Rerank | 在 Top10 内按问题—段落相关性精排 | 依赖初筛质量；块边界混杂时仍难完美 |

### 4. 结论

1. **工程上能跑通。** 不改 Chroma，用云端 `bge-reranker-v2-m3` 就能对 Hybrid 候选做二次精排，并已接到生产 `retrieve`。
2. **职责比较清楚。** Hybrid 负责召回和粗排；Rerank 负责候选内精排，不扩大召回范围。
3. **问题定位比较准。** 直接回应实验二「聘用程序在 Top3 但不是 Top1」这类情况：相关块已经在池子里时，用更强的 query—document 相关性模型，而不是硬说 Hybrid 全面优于 Dense。
4. **效果表述要克制。** 这一阶段还是以探针预览和粗粒度金标位次为主；有无 Rerank 的 Ragas 定量结果见实验四。

### 5. 对项目的影响

相关能力已落地：

- `app/rag/rerank.py`：硅基流动 Rerank 封装；
- `app/rag/chain.py`：`retrieve = hybrid_search(10) → rerank_documents(top_n=3)`；
- `scripts/retrieve_probe.py`：增加 Rerank 预览与 Hybrid / Rerank 位次对照；
- 依赖：`httpx`（调用 `/v1/rerank`）。

生产检索链路现在是：

```text
问题 → Hybrid Top10 → Rerank Top3 → Prompt → DeepSeek
```

### 6. 实验局限

1. 探针问句数量有限，金标多为单关键词，不能替代正式 Hit@3 / MRR；
2. 这一阶段仍以探针预览为主；Context Precision、Context Recall、Faithfulness、Answer Relevancy 的有无 Rerank 对照见实验四；
3. Rerank 多一次外部 API 调用，会带来延迟，也依赖密钥、网络和超时设置；
4. 切块边界仍可能导致职责与条件混在一块，精排只能缓解排序，拆不开语义。

这一部分更适合说成：Rerank 已经接上，针对实验二的「排不准」给了一个工程解法；定量上有没有稳定收益，看实验四。

## 实验四：Ragas 有无 Rerank 定量对照（50 题）

### 1. 实验目标

实验三说明 Rerank 能接上、探针里也能看到排序变化；上一版还曾用 15 题做过一轮 Ragas 对照。为降低小样本波动、覆盖更多规章主题，这次把 Ground Truth 扩到 **50 题**，对「无 Rerank」和「有 Rerank」两条完整检索—生成链路再跑同一套四指标。

相对 15 题那轮，这次主要想确认：

1. 样本量变大后，Rerank 对 Context Precision 的收益是否还在？
2. Context Recall 是否仍像 15 题那样「两组完全相同」，还是会因最终 Top3 置换而变化？
3. Faithfulness / Answer Relevancy 在更大题集上怎么走？
4. 哪些题两边 Recall 仍为 0（Rerank 帮不上，要回头查初筛 / 切块）？

### 2. 实验设置

| 项目 | 设置 |
|------|------|
| 评估集 | `evaluation/ground_truth.json`（**50** 条问句 + 参考答案） |
| 无 Rerank | `hybrid_search(n_results=10)` 后取前 3 段 |
| 有 Rerank | `hybrid_search(10)` → `rerank_documents(..., top_n=3)` |
| 生成模型 | DeepSeek `deepseek-chat`（`temperature=0`） |
| 评估脚本 | `evaluation/eval_with_ragas.py`（`--mode no_rerank` / `rerank`） |
| 评判 LLM | DeepSeek `deepseek-chat`（Ragas judge） |
| 评判 Embedding | `BAAI/bge-large-zh-v1.5`（硅基流动，用于 Answer Relevancy） |
| 指标 | Context Precision、Context Recall、Faithfulness、Answer Relevancy |
| 汇总结果 | `evaluation/results_no_rerank.json`、`evaluation/results_rerank.json` |
| 逐题明细 | `evaluation/results_*_detail.json` |
| 跑分时间 | `no_rerank`：2026-08-04；`rerank`：2026-08-05 |

**指标各自在看什么（方便后面解读）：**

| 指标 | 大致含义 |
|------|----------|
| Context Precision | 最终 Top3 里，和参考答案相关的块是否更多、排得更靠前 |
| Context Recall | 参考答案里的关键信息，最终 Top3 有没有覆盖到 |
| Faithfulness | 模型回答有没有超出检索上下文乱编 |
| Answer Relevancy | 从答案反推问题再和原问题比向量相似度，看答得是否贴题 |

**题集主题分布（50 题，完整题单见 `ground_truth.json`）：**

| 主题 | 题数（约） | 主题 | 题数（约） |
|------|----------:|------|----------:|
| 研究生规章 | 9 | 实习 | 6 |
| 研究生资助 | 5 | 处分 | 4 |
| 学籍 / 学分 | 4 | 资助 | 3 |
| 考试 | 2 | 教学管理 | 2 |
| 学位 | 2 | 申诉 | 2 |
| 体测 | 2 | 转学 | 2 |
| 毕业论文 | 2 | 转专业 / 见习 / 公寓 / 评优等 | 其余 |

两组模式共用同一份金标，生成侧 prompt 也保持一致，尽量只让「有没有 Rerank」成为变量。

### 3. 结果对比

#### 3.1 指标总表

| 指标 | 无 Rerank | 有 Rerank | 差值（有 − 无） |
|------|----------:|----------:|----------------:|
| Context Precision | 0.730 | 0.792 | **+0.062** |
| Context Recall | 0.743 | 0.880 | **+0.137** |
| Faithfulness | 0.857 | 0.890 | +0.033 |
| Answer Relevancy | 0.647 | 0.825 | **+0.178** |
| 样本量 n | 50 | 50 | — |

原始分数来自：

| 模式 | context_precision | context_recall | faithfulness | answer_relevancy |
|------|------------------:|---------------:|-------------:|-----------------:|
| `no_rerank` | 0.729591836672534 | 0.7433333333333333 | 0.8567720652813533 | 0.6472085752145795 |
| `rerank` | 0.7916666666029166 | 0.88 | 0.8900711102622867 | 0.8248636857740288 |

（对照：上一版 15 题上 Precision 约 0.67→0.90、Recall 两边同为 0.83。扩到 50 题后绝对值有变化，但「有 Rerank 更好」的方向一致。）

#### 3.2 解读

1. **Context Precision 仍提升（约 0.73 → 0.79）。**  
   幅度小于 15 题那轮（当时约 +0.23），更符合「题集变大、题型变杂之后均值被拉平」的预期。逐题看：约 19 题 Precision 上升、约 8 题下降，整体仍支持精排改善 Top3 排序质量。

2. **Context Recall 这次明显上升（约 0.74 → 0.88）。**  
   这和 15 题「两组 Recall 完全相同」不同，并不矛盾：  
   - 召回**上界**仍由 Hybrid Top10 决定，Rerank 不能捞池外文档；  
   - 但最终只取 Top3，重排会改变「哪三段进生成」——若原先被挤出 Top3 的关键段落被推回来，**最终 Top3 对参考答案的覆盖**就会上升。  
   逐题：约 **13** 题 Recall 上升、**0** 题下降；两边仍同为 0 的有 2 题（勤工助学申请流程、可申诉情形范围等），这类仍属初筛 / 切块问题，精排帮不上。

3. **Faithfulness 小幅上升（0.857 → 0.890）。**  
   两组都还算忠实。差值不大，n=50 下可写成略有改善：Top3 更干净时，生成更不容易被次相关段落带偏。

4. **Answer Relevancy 提升最显眼（0.647 → 0.825）。**  
   说明精排后的答案在「答得是否贴题」上改善更明显。无 Rerank 时 Relevancy 偏低，也可能反映部分题把次相关规章段落拼进答案、反推问题后与原问偏离。

5. **用 Recall × Faithfulness 做简单诊断。**  
   - 有 Rerank 后整体 Recall 较高、Faithfulness 也高 → 生成侧相对健康。  
   - 仍要把两边 Recall=0 的题当作优化清单（查 Hybrid Top10、切块边界、金标与入库文本是否对齐）。

### 4. 结论

1. **定量对照已按 50 题 + 四指标跑通。** 汇总和逐题结果分别落在 `evaluation/results_*.json` 与 `evaluation/results_*_detail.json`。
2. **Rerank 在更大题集上仍值得保留。** Precision、Recall、Faithfulness、Answer Relevancy 四项均高于无精排基线；生产建议继续 `hybrid_search(10) → rerank_documents(3)`。
3. **Recall 可变，不等于「精排扩大了全库召回」。** 更准确的说法是：精排改变了最终 Top3 的构成，从而改变了对参考答案关键信息的覆盖；池外漏召回仍要回到 Hybrid / 切块。
4. **相对 15 题小样本，50 题结论更稳，但 Precision 增益更「温和」。** 不宜再只引用 0.67→0.90 那组数字作为对外唯一结论。
5. **下一轮优先：** 啃掉两边 Recall 仍为 0 的题；并对 Precision 下降的个例做人工抽查（金标写法 vs 入库文本）。

### 5. 实验局限

1. 50 题覆盖面好于 15 题，相对全库规章问答仍有限，结论不宜外推过头；
2. Ragas 指标依赖评判 LLM / Embedding，分数本身会有波动；
3. Context Recall 上升不代表每题检索文件一定换对了，需要结合明细里的 `retrieved_contexts` 抽查；
4. 个别低分题需要人工核对：是检索真没命中，还是参考答案写法和入库文本不一致；
5. 还没有单独做「只改切块 / 只扩候选数」的对照，无法量化它们各自对 Recall 的贡献。

## 实验五：拒答 / 幻觉行为小金标（30 题）

### 1. 实验目标

Ragas 那套指标主要覆盖「该答」题的检索质量与忠实度，对「该拒」和「部分答」不敏感。学校规章问答里，这两类行为同样重要：无关或库外时要整句拒答，相关但缺细节时要答大意并声明未覆盖，不能编数字。

相对上一版 15 题行为集，这次扩成 **30 题**，并改成均衡配比，人工判：

1. **误拒**：期望「答」或「部分答」，却整句输出拒答固定句；
2. **幻觉**：编造资料 / 金标没有的金额、名额、电话、流程等。

想回答的问题：当前 Prompt（只依据检索资料作答、部分相关可部分答、无关才拒答）在生产链路下行为是否靠谱，而不只凭感觉调 Prompt。

### 2. 实验设置

| 项目 | 设置 |
|------|------|
| 评估集 | `evaluation/refusal_gold.json`（**30** 题） |
| 题型配比 | 该答 **10** / 部分答 **10** / 该拒 **10** |
| 检索 | `hybrid_search(10)` → `rerank_documents(..., top_n=3)`（与生产一致） |
| 生成 | 复用 `evaluation/eval_with_ragas.py` 的 `get_contexts` + `get_answer`（`deepseek-chat`，`temperature=0`） |
| 跑分脚本 | `evaluation/eval_refusal.py` |
| 原始输出 | `evaluation/refusal_run.json` |
| 拒答固定句 | `抱歉，学校官方文档未收录此条例`（多一个字也算偏） |

**行为判定规则（与 `app/rag/chain.py` 中 SYSTEM_PROMPT 对齐）：**

| 期望 | 判对标准 |
|------|----------|
| 答 | 命中金标要点；不要拒答句；不要追加「联系教务处」 |
| 拒 | 答案整句等于拒答固定句 |
| 部分答 | 能说资料支持的大意 + 标明未覆盖 + 末尾有「具体请联系教务处核实」；禁止编造 `forbidden` 中的数字 / 电话等 |

**题单摘要：**

| 类型 | ID | 示例问句 |
|------|-----|----------|
| 该答 | a1–a10 | 处分种类、申诉时限、学制年限、优秀毕业生比例、体测结业分、转学受理月份、研究生奖助金额、论文复制比、教育实习学期、公寓日租标准等 |
| 部分答 | p1–p10 | 转专业学费具体多少、勤工时薪、三助津贴、心理求助电话、实习生活补贴、转专业名额、毕设查重系统、补考具体日期教室、研究生宿舍房型、助学贷款绑定哪家银行卡等 |
| 该拒 | r1–r10 | 食堂价格、校车时刻、校园卡充值、天气预报、图书馆开放时间、WiFi 密码、快递驿站位置、教务处楼号电话、暑假放假日期、教务系统网址等 |

造题原则：该拒题选库外 / 运营生活信息；部分答题选「规章有原则、缺用户要的精确字段」；该答题选 PDF 中有明确条款的事实问。

### 3. 结果

#### 3.1 总表

| 指标 | 结果 |
|------|------|
| 样本量 | 30 |
| 行为准确（答 / 拒 / 部分答类型对） | **27/30** |
| 误拒 | **3/30**（p4、p6、p9） |
| 幻觉 | **0/30** |

#### 3.2 分项

**该答（a1–a10）：** 十题均未整句拒答；金标要点基本齐全（处分五种、申诉 10 个工作日、学制 3 年 / 最长 5 年、优秀毕业生 15% / 绩点 2.5、体测 50 分结业、转学 4 月与 10 月、助学金 6000 / 学业奖三档金额、复制比 ≤15%、实习第七学期 1 学期、公寓 150 元/间·天）。  
风格问题：a6 答对了受理月份，但仍追加了「具体请联系教务处核实」（该答题不宜加这句，不记入误拒 / 幻觉）。

**该拒（r1–r10）：** 十题答案均一字不差等于拒答固定句。食堂、班车、校园卡、天气、图书馆、WiFi、驿站、办公电话、暑假、教务网址等均未编造细节。

**部分答（p1–p10）：**

| ID | 判定 | 说明 |
|----|------|------|
| p1 转专业学费 | 过 | 给出按新专业标准缴费，声明无具体金额，末尾联系教务处 |
| p2 勤工时薪 | 过 | 说明参照湛江市最低工资 / 最低小时工资，声明无固定数值 |
| p3 三助津贴 | 过 | 说明参照广东省最低工资、一般按每月 40 小时计，声明无具体数额 |
| **p4 心理求助电话** | **误拒** | 整句拒答；应按部分答说明辅导站 / 干预机制，并声明无电话号码 |
| p5 实习生活补贴 | 过 | 说明由受援方支付交通与生活补助、文档无具体补贴金额；末尾联系教务处（顺带提到住宿报销上限，属检索到的相关条款，未把「生活补贴」编成死数） |
| **p6 转专业名额** | **误拒** | 整句拒答；应说明有转专业条件与程序，并声明无当年各专业名额 |
| p7 毕设查重系统 | 过 | 声明无系统名与免费次数，末尾联系教务处；未编造系统名 |
| p8 补考具体日期教室 | 过 | 给出「下一学期第 2–3 周」的制度性安排，声明无具体日期 / 教室 |
| **p9 研究生宿舍房型** | **误拒** | 整句拒答；若上下文仅有对外有偿租公寓等近邻条款，仍宜说明「未规定在校生日常宿舍分配」，而不是整句拒答 |
| p10 助学贷款绑定银行 | 过 | 说明国开行广东分行办理、还款进指定支付宝账号等已有信息，声明未要求绑定特定银行卡 |

### 4. 结论

1. **拒答行为回归已按 30 题均衡集跑通。** 金标、脚本与原始输出分别落在 `refusal_gold.json`、`eval_refusal.py`、`refusal_run.json`。
2. **当前短板仍不在「乱编」，而在「过拒」。** 幻觉 0/30；三个失败全是部分答题误拒（p4 / p6 / p9）——模型在「有相关制度、缺用户要的精确字段」时偏保守，直接走整句拒答。相对上一版 15 题（误拒 1），题集加大后误拒绝对次数上升，但模式一致。
3. **该拒仍然很稳。** r1–r10 全过，说明库外生活 / 运营类问题上，固定句拒答可靠。
4. **该答整体可用。** 10 题均未误拒；需留意个别题多余追加「联系教务处」（a6）。
5. **和 Ragas 的分工：** `ground_truth.json`（50 题）看该答题的 Precision / Recall / Faithfulness；`refusal_gold.json`（30 题）看拒答与部分答行为。两套一起，才能说「不只凭感觉调 Prompt」。
6. **下一轮优先：** 强化 Prompt「部分相关时先答能支持的部分，再声明未覆盖」；用 p4 / p6 / p9 作回归哨兵，改完后重跑 `eval_refusal.py`，目标把误拒压到 0。

### 5. 实验局限

1. 30 题行为集好于 15 题，仍不能代表全部边缘 case；
2. 人工判标存在一定主观性（例如 a6 多余「联系教务处」、p5 是否算跨文档引用，是否单独扣分）；
3. 回归脚本生成模型为 `deepseek-chat`，与生产 `chain.py` 中的模型版本可能不完全同一；结论写清模型版本更稳妥；
4. 未做「改 Prompt 前后」的二次对照，目前是扩题后的基线快照。

## 总结

整条优化路径可以概括成：

1. **切块**：用 Recursive + 256/50，减少规章条款被硬切腰斩；
2. **混合检索**：Dense + BM25 + RRF，稳住目标文档，改善关键字侧；
3. **Rerank**：在 Hybrid Top10 内精排，把更贴问题的段落推到生成用的 Top3；
4. **Ragas 对照（50 题）**：有 Rerank 时 Precision / Recall / Faithfulness / Answer Relevancy 均高于无精排；Recall 上升来自最终 Top3 置换，不是全库召回变大；
5. **拒答小金标（30 题）**：该答 10 / 部分答 10 / 该拒 10；行为准确 27/30，误拒 3、幻觉 0；强项是该拒，短板是缺细节时过拒。

当前两条线可以并行：检索侧继续啃两边 Recall=0 的题（切分 / 分词 / 初筛）；生成侧用拒答回归集盯住「过拒」，改 Prompt 后重跑对比。
